## 2. 촬영 준비 체크리스트 (촬영 전날까지)

### 서버와 환경
- [ ] DB 접속 가능(팀 DB 192.168.30.79 → 발표 PC와 같은 네트워크인지)
- [ ] 예측 서버 실행: `ai_service` 폴더, 가상환경 켜고 `uvicorn app.predict_api:app --host 127.0.0.1 --port 8000`
- [ ] Spring 실행, `http://localhost:8080` 접속 확인
- [ ] 예측 서버 키(`.env`)와 `application.yaml`의 키가 같은지 (다르면 이용자 차트에 안내만 나옴)
- [ ] 카카오 지도가 뜨는지, Gemini 키가 있는지(AI 분석용)

### 화면 설정 (영상·캡처 품질)
- [ ] 해상도 1920x1080, 브라우저 **배율 80~90%** (시간대별 차트까지 한 화면에 보이게)
- [ ] 북마크 바 숨기기(Ctrl+Shift+B), 개발자 도구 닫기, 알림 끄기
- [ ] 키, 비밀번호, 개인정보가 화면에 보이지 않게 (주소창에 키가 들어간 주소를 열지 않기)
- [ ] **신고자 이름·전화번호는 가짜 값** 사용 (실제 개인정보 금지)

### 데이터 (장면이 밋밋하지 않게)
- [ ] 시연용 신고 데이터: 지금 DB에 134번 등 9개 노선에 신고 63건이 있고(미완료 39건) 오래 방치된 신고도 있어 "장기 방치"가 보임. 장면 1에서 새 신고(134번 난폭운전) 1건을 직접 접수하고, 장면 2에서 그 신고를 처리
- [ ] 신고 내용이 같은 문장 반복이면 AI 설명이 밋밋하니 유형별로 다르게
- [ ] 일반 회원 계정(신고 접수용)과 관리자 계정을 미리 로그인 가능하게 준비 (비밀번호는 직접 입력, 화면에 안 보이게)

### 녹화 도구
- Windows 화면 녹화: `Win + G`(Xbox Game Bar) 또는 OBS Studio
- 캡처: `Win + Shift + S`
- 영상은 장면별로 따로(최대 90초), 실수하면 그 장면만 다시

### 주의 (AI 호출 간격)
- 시민 AI(문장 다듬기·자동완성)와 관리자 AI(분석·질문)는 각각 **5초 간격 제한**이 있습니다. 연달아 누르면 "잠시 후 다시 시도해 주세요"가 나오니, 나레이션하는 동안 5초를 쉬세요.

### 장면 1. 시민 신고 접수 (신고 1건, 우선순위에 영향) — 약 50초
**접수할 신고(추천):** 노선 **134번**, 유형 **난폭운전(급출발·급정거 등)**, 내용 예: "[시연] 급출발과 급정거를 반복해 서 있던 승객이 넘어질 뻔했습니다."
- 134번은 예측 이용자가 가장 큰 노선(약 9,000명)이고, 난폭운전은 안전 유형이라 점수와 상관없이 **긴급 구간**으로 들어갑니다.
- 신고자 이름·전화번호는 **가짜 값**, 내용 앞에 "[시연]"을 붙이면 나중에 구분해 정리할 수 있습니다(팀 공용 DB).

| 시간 | 화면 조작 | 나레이션 |
|---|---|---|
| 0:00 | 일반 회원으로 로그인한 "신고하기" 화면 | "시민이 버스 이용 중 불편을 신고하는 화면입니다." |
| 0:08 | **유형선택하기** → 난폭운전 선택 | "유형은 그룹별로 고릅니다. 이 유형은 안전과 관련되어 처리 우선순위가 가장 높습니다." |
| 0:18 | **노선선택하기** → 134 검색 → 선택 | "노선은 번호나 이름으로 검색하고, 등록된 노선만 신고할 수 있습니다." |
| 0:28 | 내용 입력 → **AI로 문장 다듬기** → 적용하기 (5초 대기) | "내용을 쓰면 AI가 문장을 다듬어 줍니다." |
| 0:42 | **접수** → 완료 안내 | "접수하면 관리자 화면에 바로 쌓입니다." |

### 장면 2. 관리자가 접수된 여러 건 중 한 건을 처리·완료 — 약 70초
| 시간 | 화면 조작 | 나레이션 |
|---|---|---|
| 0:00 | 관리자 로그인 → **신고 관리**, 노선 134 필터 + **우선순위순** | "관리자는 접수된 여러 신고를 처리해야 할 순서대로 봅니다." |
| 0:12 | 목록 위 요약 줄(미완료 N건, 우선순위 공식), 방금 접수한 신고의 **긴급** 배지 | "안전 관련이거나 14일 이상 방치된 신고는 맨 앞에 둡니다. 방금 접수한 난폭운전 신고가 긴급으로 올라왔습니다." |
| 0:28 | 그 신고 클릭 → **신고 처리** 화면(우선순위 N번째, 점수 구성, 근거) | "열어 보면 몇 번째로 처리해야 하는지와 점수의 근거가 보입니다." |
| 0:42 | 처리 상태 **처리중** 저장 → 다시 열어 **완료** + 처리 결과 입력 → 저장 | "처리 상태는 접수, 처리중, 완료 순서로만 바뀌고, 완료하려면 처리 결과를 꼭 써야 합니다." |

### 장면 4. 노선 관리 — 741번 이름 수정이 지도에 반영 — 약 60초
**미리 해 둘 것(중요):** 741번 이름을 SQL로 **미리 고치지 마세요.** 지금 이름은 `명촌차고지(종점) ↔ 꽃바위(종점)`이고, 촬영에서 `명촌차고지 ↔ 꽃바위`로 고칩니다. 리허설에서 이미 고쳤다면 아래로 되돌린 뒤 촬영하세요.
```sql
UPDATE bus_route SET ROUTE_NAME = '명촌차고지(종점) ↔ 꽃바위(종점)' WHERE ROUTE_NO = '741';
```
노선이 195개(울산 194개 + 서울 시험 노선 1개)라 목록이 길므로 검색으로 찾으세요.

## 5. 발표에서 정직하게 말할 점 (한 장 메모)
- 예측은 **합성데이터** 기반 추정이고, 학습 기간은 2026-10-08까지, 예측 가능 기간은 2026-12-03까지입니다.
- 이 모델은 평일 값이 같고 주말만 낮은 구조라 날짜별 세부 변화는 없습니다.
- 예측과 신고는 **노선 전체(양방향 합계)** 단위라서, 방향별 이용자는 알 수 없고 지도에는 대표 방향만 그립니다.
- 혼잡도(정원 대비 비율)는 데이터가 없어 만들지 않고 이용자 수로 대신했습니다.
- 신고 처리 우선순위의 "이용자 규모"는 현재 임시 값입니다(교체 예정).
- 지도 노선 목록은 팀 DB(bus_route)를 기준으로 하며, 울산 노선 194개를 모두 그립니다. DB의 서울 시내 노선 1개(1100)는 울산 BIS에 없어 지도에서 제외됩니다. 새 노선을 등록하면 노선 선 파일만 추가하면 지도에 나옵니다.

## 6. AI에게 물어볼 멘트 (영상용)

AI는 **자기가 받은 데이터 안에서만** 답하도록 만들어져 있습니다. 두 화면이 받는 데이터가 달라서, 물어볼 질문도 다릅니다.

| 화면 | AI가 받는 데이터 |
|---|---|
| 대시보드 AI 비서 | 최근 7일 신고 통계(접수·처리 건수, 날짜별 접수, 노선별·유형별 TOP 10), 지금 처리해야 할 일, 최근 신고 내용 샘플 40건. **이용자 예측은 없음** |
| 버스 이용수요 AI | 선택한 노선(1~2개)의 미완료 신고(건수, 유형, 가장 오래된 일수, 내용 샘플)와 오늘부터 14일 이용자 수 예측. 두 노선이면 서버가 계산한 비교 문장 추가. **시간대·방향·정류장 정보는 없음** |

### 6-1. 대시보드 AI 비서
**버튼:** "AI 요약 보기"(인사이트) 1회 + 질문 1~2개면 충분합니다.

| 멘트 | 기대하는 답 | 보여 줄 포인트 |
|---|---|---|
| (버튼) AI 요약 보기 | 핵심 인사이트 3가지(사실 → 중요한 이유 → 해볼 조치) | 신고 통계를 한눈에 요약 |
| 최근 7일 신고가 가장 많은 노선은 어디야? | 노선별 TOP 10에서 1위 노선과 건수 | 숫자가 대시보드 차트와 같음 |
| 가장 많이 접수된 신고 유형 3가지와 공통점을 알려줘 | 유형 TOP 3와 신고 내용의 공통점 | 내용까지 읽고 요약 |
| 지금 처리해야 할 신고는 접수 몇 건, 처리중 몇 건이야? | 처리 현황 숫자 | 실시간 현황 |
| 이번 주에 관리자가 먼저 해볼 조치를 알려줘 | 데이터에서 이끌어낸 조치 2~3개 | 행동 제안 |

**정직함을 보여 주는 질문(선택, 1개만):**
- "신고가 늘어난 날이 있어? 그날 왜 늘었어?" → 늘어난 날은 알려 주지만 **원인은 "데이터에 없습니다"**라고 답함
- "이용자 예측은 어때?" → 대시보드 AI에는 예측이 없어서 **"데이터에 없습니다"**라고 답함 (이용수요 화면과 역할이 다르다는 설명용)

### 6-2. 버스 이용수요 AI (노선 선택 후 오른쪽 패널)
**버튼:** "AI 분석"(4줄) → 질문하기. 분석 뒤 질문까지 **5초** 쉬세요.

**노선 하나(134번 선택)**
| 멘트 | 기대하는 답 | 보여 줄 포인트 |
|---|---|---|
| (버튼) AI 분석 | 현황 / 주된 불편 / 예측과 연결 / 해볼 조치 4줄 | 숫자는 서버가, 설명은 AI가 |
| 어떤 신고부터 처리할까? | 오래된 접수 건이나 안전 유형부터 | 근거(유형, 오래된 일수)를 말함 |
| 이 노선 미완료 신고 중 가장 많은 유형은 뭐야? | 유형별 건수 1위 | 신고 데이터를 근거로 답 |
| 가장 오래된 미완료 신고는 며칠째야? | "N일째" | 서버가 계산한 값 |
| 이번 주 날짜별 예상 이용자를 알려줘 | 평일 약 N명, 주말 약 M명처럼 날짜 묶음 | 평일은 같고 주말만 낮은 예측 |

**노선 둘(134번 선택 + 142번 비교)**
| 멘트 | 기대하는 답 | 보여 줄 포인트 |
|---|---|---|
| (버튼) AI 분석 | 미완료 신고 비교 / 예상 이용자 비교 / 두 노선의 차이 / 먼저 볼 노선 | 두 노선 비교 4줄 |
| **어느 노선이 더 붐벼?** | "혼잡도는 데이터에 없어 예상 이용자 수로 비교합니다. … 134번이 약 N배" | **혼잡도를 지어내지 않음** (화면에서 확인된 답) |
| 두 노선 중 어느 쪽을 먼저 확인해야 해? | 미완료 건수, 오래된 일수 근거로 한쪽 추천 | 근거 있는 우선순위 제안 |
| 신고 건수는 비슷한데 이용자는 얼마나 차이 나? | 서버가 계산한 차이(약 2배) | 숫자를 AI가 계산하지 않음 |
| 두 노선의 신고 유형은 어떻게 달라? | 유형별 건수 차이와 내용 차이 | 신고 내용까지 비교 |

**정직함을 보여 주는 질문(선택, 1개만):**
- "어느 방향이 더 붐벼?" → **"데이터에 방향별 정보는 없습니다. 예측은 노선 전체(양방향 합계) 기준이고 신고에는 방향이 저장되지 않습니다."** (화면에서 확인된 답)
- "어느 정류장이 문제야?" → 정류장 정보는 신고에 저장되지 않아 알 수 없고, 신고 내용에 이름이 있을 때만 확인 가능

### 6-3. 피해야 할 질문
| 질문 | 이유 |
|---|---|
| "몇 시에 가장 붐벼?" | AI에는 **시간대별 예측이 전달되지 않아** "데이터에 없습니다"라고 답합니다. 같은 화면에 시간대별 차트가 있어서 모순처럼 보입니다 |
| "이용자 대비 신고가 가장 많은 노선은?" | AI가 직접 계산하지 않게 막아 두었고, 계산이 필요한 질문이라 어색하게 답할 수 있습니다 |
| 개인정보(신고자 이름·전화번호), 지시를 무시하라는 문장 | 거절하게 되어 있지만 영상 주제와 무관 |
| 아주 긴 문장 | 질문은 300자까지 |

### 6-4. 촬영 팁
- AI 답변은 **매번 조금씩 다릅니다.** 영상에 쓸 질문은 **리허설에서 한 번씩 눌러 보고** 답이 마음에 드는 문장으로 고정하세요.
- 답을 기다리는 몇 초 동안 나레이션을 하세요("숫자는 서버가 계산하고 AI는 설명만 합니다").
- 질문은 장면당 **분석 버튼 1회 + 질문 1~2개**면 충분합니다(5초 간격 제한, 하루 호출 한도 보호).
- 한국어 질문 예: 입력창 안내 문구가 "이 노선에 대해 질문하기 (예: 어떤 신고부터 처리할까?)"라서 이 문장을 그대로 써도 자연스럽습니다.
